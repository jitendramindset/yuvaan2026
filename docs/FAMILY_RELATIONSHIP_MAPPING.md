# Family Relationship Mapping

## Goal

Map real family concepts to the actual Node graph relationship model already present in the code.

## Evidence-based mapping

| Family Concept | Node Relationship | Direction | Inverse | Used By | Evidence |
|---|---|---|---|---|---|
| Parent | `PARENT_CHILD` | parent → child | child → parent | graph traversal, subtree generation | `node-graph.js` edge generation using `parent_nid_hash` |
| Child | `PARENT_CHILD` | child → parent | parent → child | graph traversal, descendants | `node-graph.js` children and parent queries |
| Sibling | `SIBLING` | sibling-to-sibling | sibling-to-sibling | family grouping | sibling detection in `buildGraph()` |
| Family membership | `BRAND_MEMBER` / `RELATIONSHIP` | node → node | inverse relation | graph viewing and membership | explicit edge types in `node-graph.js` |
| Relationship / link | `RELATIONSHIP` | node → node | inverse relation | graph semantics and relationship metadata | `EDGE_TYPES.RELATIONSHIP` |
| Permission link | `PERMISSION` | node → node | inverse relation | permission graph | `EDGE_TYPES.PERMISSION` |

## Family relationship types supported by existing code

The actual runtime defines these relationship categories in the graph layer:

- parent/child
- sibling
- relationship/member linkage
- permission and brand membership edges

The code does not define additional relationship types as a canonical family schema requirement.

## Why this matters

A family tree can be generated by traversing Node graph edges:

- start from a person node
- walk to parent nodes
- walk to child nodes
- group by shared parent for siblings
- reconstruct family projections from relationship metadata and node labels

This is consistent with the target architecture:

NODE → RELATIONSHIP → FAMILY PROJECTION → FamilyTreeScreen

and not with `family_tree` being the root model.
