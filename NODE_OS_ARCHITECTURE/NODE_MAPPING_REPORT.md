## 1. The Core Truth: `node_core` is already the universal node table

`node_core` is the single source of truth. Every node — user, family member, post, widget, plugin, wallet — is a row here, distinguished by `node_type` and carried payload blobs.

| Concern | Column(s) | Notes |
|---|---|---|
| Identity | `row_id` (PK), `owner_id` (uuid→users.id), `nid_hash` (sha256) | `nid_hash` is the node address used everywhere |
| Type | `node_type`, `node_state` (ACTIVE/INACTIVE/SUSPENDED/ARCHIVED) | living vs non-living |
| Hierarchy | `parent_nid_hash` (self-FK), `node_depth` | tree; dharma caps depth at 20 |
| Payload (bytea, hex-JSON) | `dna_blob`, `field_map`, `perm_blob`, `rule_blob`, `runtime_blob`, `memory_blob`, `ui_blob`, `sys_blob` | decode: `JSON.parse(Buffer.from(hex.slice(2),'hex'))` |
| Semantics | `vec_embedding` (pgvector 1536) | per-node embedding |
| Governance | `karma_score`, `trust_score`, `reputation_level` | mirrored into log tables |
| Brand | `brand_root`, DNA `brand_scope` | resolves the active brand |
| Economy | `wallet_id` (→node_wallet) | |
| Sync | `sync_version`, `last_sync_at`, `state_hash` | conflict resolution |
| Security | `pin_hash`, `qr_token_hash`, `device_fingerprint`, `encryption_key_ref`, `privacy_mode`, `permission_scope` | |
| AI | `node_system_prompt`, `prompt_version` | evolves with karma |
| Lifecycle | `is_cold`, `sleep_after`, `wakeup_at`, `health_score` | cold-storage / wake |

**Mapping rule:** A new "thing" is a `node_core` row + relationships. It is NOT a new table unless it is high-volume relational data (transactions, logs, vectors) that already has a home below.

Everything in the vision prompt maps to **existing** storage. The `node_type` column carries the distinction.

| Vision "Node" | node_type | Lives in | Relationship store |
|---|---|---|---|
| User | `user` | node_core | node_permission |
| Profile | `profile` | node_core (field_map) | parent_nid_hash → user |
| Family / Friend | `family_member` / `friend` | node_core | node_permission (relationship_scope=family) |
| Group | `group` | node_group + node_group_member | |
| Post / Comment | `post` / `comment` | node_core (non-living) | parent_nid_hash |
| Wallet | — | node_wallet | node_core.wallet_id |
| Asset / Document | `document` | node_core + business_documents | |

## 4. Gaps (what is genuinely missing — see IMPLEMENTATION_TASKS.md)

These are **not** missing tables — they are missing **wiring or UI**:

1. **`_uiBootstrap` reads `dashboard_layouts`/`dashboard_widgets` but ignores `node_type='layout_schema'` nodes.** Brand defaults are currently hardcoded in `kernel-executor.js` (acceptable as fallback) — persistence path to `dashboard_layouts` is the missing link for user customization.
2. **Frontend screens** (Family Tree, Network, Wallet, Marketplace, Plugin Center, Profile, Settings, Admin) are not yet routes — the kernel can already serve their data; the render engine needs the widget types + screens.
3. **`node_trust_state`** exists and `trust-engine.js` writes it — the vision's "node_trust_state" requirement is already satisfied (the prompt lists it as to-create; it exists).
4. **Layout-instance cloning** ("user receives cloned layout instance, never modify default") — needs a `clone_layout` action that copies a brand default into a user-owned `dashboard_layouts` row.

## 5. Anti-duplication checklist (enforce in every PR)

- [ ] New entity? → `node_core` row, not a new table.
- [ ] New relationship? → `node_permission` (with `relationship_scope`), not a join table.
- [ ] New transaction/value flow? → `node_transaction` + `contribution_graph`.
- [ ] New reputation signal? → `node_karma_log` / `node_trust_state`, not a new score table.
- [ ] New AI memory? → `vector_chunks` / `ai_session_memory` via `vector-manager.js`.
- [ ] New UI? → `dashboard_widgets` + `WidgetRenderer` widget type.
- [ ] New sync need? → `node_event_queue` + `node-sync.js`.

See [`KERNEL_ARCHITECTURE.md`](./KERNEL_ARCHITECTURE.md) for how these tables are orchestrated.
